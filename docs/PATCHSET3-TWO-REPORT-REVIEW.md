# Patchset-0003 — Two Human QA Reports: Difference Review

**Status:** Source-only, read-only consistency and discrepancy comparison. No independently verified game-test results exist in this project yet.

This compares two locally supplied [human QA self-report records](PATCHSET3-MANUAL-QA-RECORD.md) against the **same regenerated, hypothetical patchset-0003 QA plan**. The plan still has six permitted cases (base, U, J, J+U, C, C+U) and two prohibited C+J combinations. The comparator is **not a witness**, cannot establish that two people were involved, and cannot independently authenticate either document.

## Why this is necessary

A single apparently complete PASS record may be a mistake or a fabricated document. Even **two matching** PASS records could have been copied, deliberately rewritten, backdated, or generated by the same author. The SHA-256 plan fingerprint in each record establishes only accidental reference consistency; it is not independently held authority, a signed observation, a protected time source, a verified game executable, or real gameplay evidence.

This tool therefore reports only **differences between two untrusted claims**. It never upgrades them to PASS-certified or approved.

## How to compare local records

Use Python 3.12 from a trusted checkout, with **two separate existing local private JSON records**. Do not upload screenshots, client paths, account details, characters or MPQ files to GitHub.

```powershell
python .\tools\compare_patchset3_human_reports.py --proposal .\tests\fixtures\synthetic-patch-proposal-v3.json --release-snapshot .\tests\fixtures\public-release-metadata-v1.json --report-a .\local-qa-a.json --report-b .\local-qa-b.json
```

The sample proposal/release inputs above are **fake/offline planning fixtures**, not real release approval. Substitute only previously reviewed and intentionally supplied metadata for an actual future proposal. The comparator itself **never reads an MPQ, client/WTF directory, account data or image**, and never writes any record.

Both local reports must separately pass the [strict single-report validation](PATCHSET3-MANUAL-QA-RECORD.md). It rejects omitted or reordered cases, unknown check IDs, unknown extra fields, contradictory outcomes, invalid build/locale claims, duplicate JSON keys, symlinks or oversized data *before* comparing. The regenerated plan SHA-256 must match in both reports.

## What the comparison tells you

| Classification | Interpretation |
| --- | --- |
| `IDENTICAL_RECORD_CONTENT_NOT_INDEPENDENT_EVIDENCE` | Same canonical JSON. Treat as a likely copied/identical document, **not independent verification** |
| `UNTRUSTED_REPORT_DISCREPANCIES_REQUIRE_MANUAL_REVIEW` | At least one case outcome, individual check status or bounded issue classification differs; investigate separately |
| `NO_COMPARABLE_REPORTED_TEST_EXECUTION` | No case has been reported as attempted in at least one of the reports |
| `MATCHING_UNTRUSTED_REPORTS_NOT_INDEPENDENTLY_VERIFIED` | Reported outcomes/checks/issue categories agree, but authorship, true gameplay, independent custody and authenticity remain unknown |

The output shows only **public case IDs**, disagreements on public check IDs, counts and fixed statuses. It never prints personal paths, report dates, raw hashes, proposed patch file paths or user-entered text.

**Exit codes:** `0` = internally comparable reports without detected disagreement (**still NOT approval**); `2` = bad or unreadable record/proposal; `3` = discrepancies or identical record content needing human review. A green command exit must never be interpreted as a release gate.

## What would actually establish independent evidence later?

A distinct, separately reviewed process would need the following *real* evidence, not just metadata claims:

1. A separately authorised **disposable WoW 3.3.5a build 12340/enUS client**, with the required V/Z and one of six valid optional combinations, verified against an independently trusted original/client baseline.
2. A protected, source-authenticated inventory of the actual MPQ and client hashes, with externally established rights and provenance. Merely matching a mutable public release listing is insufficient.
3. Independent tester identity/authorisation, signed evidence or equivalent independently protected attestation, time freshness and anti-replay controls, with privacy safeguards and no unnecessary account data.
4. A separately controlled evidence review that actually verifies the game interaction, visual/audio outcome, unchanged original and full account/WTF state, and correctly rejected C+J selections. Neither signature nor matching report by itself proves visual/gameplay truth.
5. An independent owner decision, after complete backups, crash/recovery proof, rightsholder permission and separate Windows accessibility checks (100%, 125%, 150%, 200% scaling, High Contrast, keyboard and screen reader).

**None of these five requirements is implemented or verified by this comparator.** A future evidence attestation must not be built from arbitrary caller-controlled secret fields or local mutable JSON and claimed to authenticate a user. It needs a separately secured trust root and explicit design review.
