# Milestone 3 — Read-only recovery conflict safeguard

**Scope: Windows PowerShell 5.1, read-only.** This is **not** an installer, undo button, restore script, source for copyrighted patches, authenticated approval or durable recovery ledger.

## Why this milestone exists

The [Recovery Preview](RECOVERY-PREVIEW.md) examines a caller-provided `session.json` and compares before/installed signatures with the currently selected client and saved original copies. In certain completed hypothetical sessions it suggests `restore_after_approval` or `remove_after_approval`.

Those suggestions are **never permission to act**. A player could have changed the file since the session; a backup could be missing, corrupt, a hard link or untrusted; or the session could be an old/replayed or partially written record. This milestone adds a read-only *preservation-first* review rather than acting on the session's suggestion.

## What's actually implemented

`tools/Review-Naxxramas-RecoverySafeguard.ps1` accepts an already-existing client directory and separately held session directory and:

1. Checks the session JSON's path ancestors for reparse points and records a SHA-256 fingerprint of the current session bytes, without treating it as authenticated.
2. Runs the existing **read-only recovery preview** once. That preview checks its allowlisted operations, before/after hashes, backup file signatures, journal state, original-file presence and backup existence.
3. Runs the existing **Win32 read-only open-file-handle inventory** for the five exact client paths (mandatory V/Z, optional J/U, realmlist). These handles are read-only and are held during hashing, then closed by the scanner.
4. Runs the original recovery preview again and rereads the session record.
5. Rejects or labels changes between observed recovery classifications, session bytes or the held-handle file state.
6. Produces **preserve-first classifications only**. It never generates a script or command to restore/remove a file.

The reviewer uses the existing allowlist: `Data/patch-V.mpq`, `Data/patch-Z.mpq`, `Data/Patch-J.mpq`, `Data/Patch-U.mpq`, `Data/enUS/realmlist.wtf`. It intentionally does not inspect unrelated account, addon or player data.

## How recovery decisions are classified

| Observed condition | Read-only classification |
| --- | --- |
| File already equals claimed original | `preserve_original_no_action` |
| Created file is already absent | `preserve_absence_no_action` |
| Current file differs from both original and installed signatures | `preserve_player_changed_file_manual_review` |
| Original backup missing or corrupt | `preserve_file_missing_or_wrong_backup` |
| Session or per-file checkpoint incomplete | `preserve_file_incomplete_record` |
| Recorded installed file still present and backup appears to match | `potential_restore_requires_independent_approval` |
| Recorded newly installed file still present | `potential_removal_requires_independent_approval` |
| Client file differs from held-handle observation during review | `preserve_file_changed_during_review` |

For the last two *potential* states, the report explicitly adds `authentic_single_use_consent_and_journal_missing`. The recovery preview's legacy suggestion is shown only as **untrusted evidence**, not a recommended action.

Any observed player edit, incomplete journal, unavailable original backup, unapproved suggestion or intra-scan inconsistency is a manual non-destructive review outcome. No file is removed or restored.

## How to run developer-only review

Use a **separate disposable test client**, an already-existing synthetic session, and Windows PowerShell 5.1:

`powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\tools\Review-Naxxramas-RecoverySafeguard.ps1" -ClientPath "D:\WoW-TEST" -SessionDirectory "F:\Test-Sessions\fixture-session-001" -Json`

Example paths are illustrative. No `session.json` is generated by the reviewer. No real installer yet creates authoritative sessions. Do **not** fabricate a session against your working client and follow its suggestions.

Output is JSON with per-file status, blockers and these unconditional flags: `review_required=true`, `preserve_player_changes=true`, `allow_file_writes=false`, `allow_automatic_resume=false`, `authorises_rollback=false`, `authorises_file_deletion=false`, `records_real_consent=false`, `protected_journal_authority_verified=false` and `public_distribution_authorised=false`.

The safest possible result (`existing_file_states_need_no_change_NOT_AUTHENTICATED`) only indicates **nothing was proposed to change**; it authenticates nothing.

## Windows tests

`powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\tests\Test-RecoverySafeguard.ps1"`

The disposable test suite creates **fake V/U files**, one prior original backup and a synthetic 3.3.5a session record. It verifies:

- Completed fake installed files are *not* approved to restore or remove.
- A player-modified V remains protected from overwriting.
- A missing or corrupted previous V backup blocks any suggestion.
- An incomplete session or per-file checkpoint is preserved for manual investigation.
- An already-original file and already-absent optional file need no changes.
- A deliberate test-only mutation to V **between two recovery previews**, via a temporary *copied* legacy reviewer, is detected.
- Path traversal is rejected; neither client, original backup nor session is written by the production review tool.

Test setup/cleanup writes **only inside a freshly created disposable temporary directory**; no real WoW clients or custom MPQs are used.

## Recovery receipt and owner claim checks

The additional [Recovery Ownership and Authority Review](RECOVERY-OWNERSHIP-AUTHORITY.md) connects this existing recovery safeguard to **actual session JSON and folder fingerprints** plus two **caller-written** proposed consent/latest-state receipts. It catches changed session bytes, wrong folder, different nonce/sequence, reported consumed/revoked/expired consent, and an authority labelled stale or missing. The new receipt checker cannot authenticate the source of either record and expressly cannot detect coherent replay of both local claims; no real recovery action is authorised.

## Critical boundaries

- **Not an atomic snapshot.** Session, file inventory and backup observations occur separately and release handles between steps. Coordinated A–B–A swaps, post-review modification and other time-of-check/time-of-use changes may escape detection.
- **Not authenticated.** All session statuses and hashes are user-written claims. A matching source/target hash does not prove original provenance, permission, trusted latest-state or prevention of replay.
- **No trust in backups.** An apparently matching original backup is not a durable, independently held, authenticated restore source. Transaction-scoped [backup checkpoints](TRANSACTION-BACKUP-CHECKPOINT.md) are also untrusted.
- **No write-capable recovery.** Any eventual writer must independently check the exact file's retained Windows handle, verify newly created original backups and journal authority, obtain genuine single-use owner consent and handle conflicts without overwriting player data.
- **No bundled or redistributable MPQs.** V/Z remain mandatory to the selected core setup; J/U remain independently optional. Rights for any public redistribution have not been established.

**No client files, personal changes, existing backups or recovery journals are modified by the reviewer.**
